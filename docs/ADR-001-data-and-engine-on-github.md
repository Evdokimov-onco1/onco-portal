# ADR-001: Данные и движок раздела «Ординатура» живут в собственном GitHub-репозитории и подключаются в Tilda через jsDelivr

**Status:** Accepted
**Date:** 2026-09-14
**Deciders:** В.И. Евдокимов (владелец репозитория и страниц Tilda), М.Ю. Федянин (владелец контента)

## Context

Раздел «Ординатура» на onco-science.ru (Tilda, проект 17587206) закрыт через Tilda Members и рендерится
одним HTML-блоком T123 на страницах `/ordinatura-year-1` и `/ordinatura-year-2`.

Есть два источника кода:

1. Пакет руководителя (31.08.2026): монолитный HTML 1,2 МБ с JSON внутри, шесть панелей, все движки
   (тесты, виртуальные пациенты, OSCE, Tumor Board) готовы. Обновление контента = перевставка мегабайта в Tilda.
2. Живая сборка исполнительницы (07.09.2026): JSON и движок вынесены в чужой публичный репозиторий
   `llcbrein-pro/onco-portal`, подключены через `cdn.jsdelivr.net/gh/...@main`. В Tilda лежит тонкий блок
   (разметка + CSS + 12 КБ скрипта). Реализованы только три панели. Результаты тестов уходят
   в Google Apps Script исполнительницы.

Ограничения:
- Tilda не даёт серверной логики и хранилища; JS выполняется только на опубликованной странице.
- Tilda API не возвращает содержимое Members-страниц, править блок можно только руками в редакторе.
- Контент (61 модуль, 633 вопроса, библиотека) будет правиться руководителем регулярно.
- Сайт не должен зависеть от аккаунтов посторонних людей.
- Ограничение размера блока T123 и кэш jsDelivr (ветка кэшируется до 12 часов, теги навсегда).

## Decision

Оставить схему «данные + движок во внешнем репозитории, тонкий блок в Tilda», но перенести её
в репозиторий под контролем кафедры (`Evdokimov-onco1/onco-portal`), версионировать релизы тегами
и подключать по тегу, а не по ветке. Движок один на обе страницы; год задаётся атрибутом контейнера
(`data-year="1"`), а не копией скрипта. Все шесть панелей и карточка модуля восстанавливаются из
пакета руководителя. Приёмник результатов тестов заменяется на свой.

## Options Considered

### Option A: Монолит руководителя (JSON зашит в HTML-блок)
| Dimension | Assessment |
|-----------|------------|
| Complexity | Low |
| Cost | Бесплатно |
| Scalability | Плохо: каждая правка контента = перевставка 1,2 МБ в редактор Tilda, риск сломать вставку |
| Team familiarity | Руководитель уже так делал |

**Pros:** ноль внешних зависимостей, страница работает даже если GitHub недоступен.
**Cons:** контент нельзя править без Tilda-редактора; нет истории изменений; блок на пределе размера; два блока (годы) расходятся.

### Option B: Данные и движок в чужом репозитории (текущее состояние)
| Dimension | Assessment |
|-----------|------------|
| Complexity | Low |
| Cost | Бесплатно |
| Scalability | Нормально |
| Team familiarity | Нет доступа к репозиторию |

**Pros:** уже работает.
**Cons:** сайт зависит от чужого аккаунта; `@main` без версий; результаты тестов уходят в чужой Google-скрипт; движок урезан.

### Option C: Свой репозиторий + jsDelivr по тегу (выбрано)
| Dimension | Assessment |
|-----------|------------|
| Complexity | Low-Med |
| Cost | Бесплатно (GitHub public + jsDelivr) |
| Scalability | Хорошо: контент правится коммитом, релиз = тег, откат = смена тега в блоке |
| Team familiarity | Пользователь работает с GitHub, руководитель может править JSON через веб-интерфейс |

**Pros:** контроль, история, воспроизводимость, один движок на все страницы, локальная разработка и тесты.
**Cons:** публичный репозиторий = публичные данные (уже так в варианте B); зависимость от CDN; правка блока в Tilda всё равно руками.

### Option D: Отдельный хостинг портала (Vercel / свой сервер) с iframe или ссылкой из Tilda
| Dimension | Assessment |
|-----------|------------|
| Complexity | Med-High |
| Cost | Бесплатно или дёшево, но появляется инфраструктура |
| Scalability | Лучшее: своя авторизация, база результатов, API |
| Team familiarity | Низкая, нужен DevOps |

**Pros:** снимает все ограничения Tilda.
**Cons:** дублирует Members-авторизацию, разрывает единый сайт, избыточно для текущего объёма.

## Trade-off Analysis

Главный конфликт: простота вставки (A) против удобства обновления контента (C). Контент будет меняться
часто, а блок в Tilda редко, поэтому переносим сложность туда, где есть git. Вариант D откладываем:
пока нет требований, которые не решаются статикой плюс лёгким приёмником результатов.

Риск CDN: jsDelivr доступен из РФ, но на случай сбоя движок показывает понятную ошибку и ссылку
на повтор; данные можно продублировать через GitHub Pages как второй URL.

## Consequences

- Легче: правка контента, ревью изменений руководителем, откат, локальное тестирование, единый код для двух лет.
- Сложнее: нужен дисциплинированный релиз (тег + смена URL в двух блоках Tilda); публичные данные в репозитории.
- Пересмотреть: приёмник результатов (Apps Script под нашим аккаунтом или иное), если понадобится
  журнал прогресса по ординатору; тогда возможен переход к варианту D для бэкенда.
