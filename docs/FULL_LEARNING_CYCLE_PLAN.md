## Цель и граница готовности

Ординатор получает полный модуль Федянина, открывает конкретную лекцию и источник, сохраняет собственные решения, проходит весь тест с результатом не ниже 70%, готовится к семинару и передаёт модуль преподавателю. Преподаватель видит ответы, фиксирует обсуждение, оценивает OSCE/Tumor Board и подтверждает модуль либо возвращает его с причиной. Сохранённые данные доступны после повторного входа с другого устройства.

Вкладки и клиентский тест уже подготовлены. Они не означают готовность кабинета преподавателя, истории попыток или публикации. Клик на лекцию означает открытие, а не доказанное освоение.

Статусы: «документировано» означает возможность из документации, «проверено» — воспроизведение в проекте. Отсутствие проверки не доказывает отсутствие функции.

| Требование | Что известно сейчас | Как проверить до выбора |
|---|---|---|
| Роли студента и преподавателя | Назначение преподавателя и интерфейс проверки описаны Tilda | Два независимых учебных аккаунта; преподаватель получает только разрешённые работы |

| Эталон после собственного ответа | Весь согласованный сценарий не проверен | До сохранения ответ недоступен через интерфейс и выдачу данных; ошибка сети не открывает эталон |

| Письменная подготовка OSCE/TB и семинар | Пока требование проекта | Независимо сохранить письменную подготовку и оценку преподавателя; у TB записывать решение каждого этапа |
| Двухстороннее завершение | Пока требование проекта | Студент не подаёт модуль без условий; преподаватель подтверждает либо возвращает с причиной; журнал хранит автора и время |

Документация Tilda описывает автоматические статусы прохождения контента; их нельзя автоматически приравнять к пользовательскому правилу «открыть лекцию и один источник». Порог в интерфейсе платформы также проверяется на точной границе, а не по названию поля.

## Проверяемые правила пилота

1. Пустой или состоящий из пробелов ответ не принимается; ошибка записи видна, текст не теряется.
2. Эталон открывается после подтверждённой записи собственного ответа; отправленная версия доступна преподавателю. Предложение реализации: исправление отдельной попыткой, без перезаписи исходного рассуждения.
3. Устные вопросы подписаны: «Подготовьте ответы: эти вопросы будут разбираться с преподавателем». В логбуке есть дата, преподаватель, отметка обсуждения и комментарий.
4. OSCE/TB имеют письменный этап и отдельную оценку семинара. Неназначенная практика обозначается пробелом, кроме подтверждённого источником исключения.
5. Зачётный тест охватывает все вопросы данного модуля. Проверяется точная доля ≥70%; отображаемое округление не меняет решение. Повторные попытки сохраняются.
6. Для заявки ординатора нужны открытие лекции, открытие одного источника, обязательные ответы и успешный тест. Преподавательское подтверждение — отдельное событие после проверки и необходимых отметок семинара/практики.
7. Возврат на доработку содержит причину; повторная сдача не стирает историю. Предложение состояний: «Изучаю» → «Передано преподавателю» → «Подтверждено» либо «На доработку».
8. Обычный ординатор не видит чужие ответы и не может выполнить преподавательское действие, в том числе прямым запросом.
9. Перезагрузка, повторный запрос и смена устройства не дают ложного успеха и не дублируют принятую работу.
10. Телефон, клавиатура и прямые ссылки работают; интерфейс показывает недостающие шаги без сплошной стены материалов.
